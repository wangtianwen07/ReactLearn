# 92 技术选型决策记录（ADR 风格）：主流 SPA（Vite）+ ToB 中后台

> 目的：统一口径，避免“边学边换”。每个决策都包含：选择/理由/替代方案/风险与缓解。

---

## ADR-001 包管理：pnpm

- **决策**：使用 pnpm（而非 npm/yarn）
- **理由**：
  - 更快、更省磁盘
  - 对 monorepo（workspace）支持好（第 5 月微前端/共享包需要）
- **替代方案**：
  - npm：通用但速度与 workspace 体验一般
  - yarn：也可，但企业中 pnpm 更常用于 monorepo
- **风险与缓解**：
  - 某些脚手架默认 npm：通过文档与 `.npmrc` 统一

---

## ADR-002 构建工具：Vite（主线 SPA）

- **决策**：SPA 使用 Vite
- **理由**：
  - 开发启动快、HMR 体验好
  - 生态成熟，适合中后台多页面开发
- **替代方案**：
  - Webpack：可控但配置成本高
  - Next.js：适合 SSR/全栈，但 ToB 中后台多数不需要全站 SSR
- **风险与缓解**：
  - 复杂构建需求：用 Vite 插件或回退到 Webpack（必要时）

---

## ADR-003 语言：TypeScript strict

- **决策**：TypeScript 开启 strict（或尽早开启）
- **理由**：
  - 中后台业务复杂，类型是“协作契约”
  - 减少空值/边界导致的线上 bug
- **替代方案**：
  - JS：学习成本更低，但长期维护成本更高
- **风险与缓解**：
  - 初期写得慢：用“先关键模块严格、逐步全局严格”的策略

---

## ADR-004 UI：Ant Design

- **决策**：使用 Ant Design
- **理由**：
  - ToB 中后台生态成熟，组件覆盖全面
  - 团队招人/协作成本低
- **替代方案**：
  - Arco Design：体验优秀
  - MUI：国际化生态强
- **风险与缓解**：
  - 样式定制复杂：统一主题策略，避免深度覆盖

---

## ADR-005 路由：React Router v6

- **决策**：React Router v6
- **理由**：
  - SPA 中事实标准
  - 嵌套路由/布局路由适合中后台
- **替代方案**：
  - TanStack Router：类型更强，但团队普及度略低
- **风险与缓解**：
  - 动态路由/权限：用守卫 + 菜单配置生成（第 4 月落地）

---

## ADR-006 服务端状态：TanStack Query（React Query）

- **决策**：服务端状态（列表/详情/字典）由 TanStack Query 管理
- **理由**：
  - 缓存、失效、并发、重试都能标准化
  - 让你少写大量“loading/error/page”样板代码
- **替代方案**：
  - SWR：也可，但 Query 的控制面更完整
  - Redux 管所有状态：不推荐（成本高、易滥用）
- **风险与缓解**：
  - 缓存键设计不当：建立 queryKey 规范

---

## ADR-007 本地状态：Zustand

- **决策**：本地 UI 状态使用 Zustand
- **理由**：
  - 轻量、易用，适合中小复杂度中后台
  - 不强迫你把所有状态“上升到全局”
- **替代方案**：
  - Redux Toolkit：更强约束，适合超大团队
  - Jotai/Recoil：也可，但企业主流度略低
- **风险与缓解**：
  - store 变大：按域拆 store，避免“全局巨石”

---

## ADR-008 请求层：Axios

- **决策**：使用 Axios 封装 apiClient
- **理由**：
  - 拦截器适合 token/错误码统一处理
  - 取消请求、兼容性成熟
- **替代方案**：
  - fetch + 封装：更原生，但要补齐拦截与错误统一
- **风险与缓解**：
  - 过度封装：保持 apiClient 轻薄，逻辑以“可测试”为准

---

## ADR-009 表单：React Hook Form + Zod

- **决策**：表单使用 RHF，校验使用 Zod
- **理由**：
  - RHF 性能好、适合复杂表单
  - Zod 提供运行时校验且能推导 TS 类型
- **替代方案**：
  - Formik：较重
  - AntD Form：可用，但复杂联动与类型一致性成本高
- **风险与缓解**：
  - 与 AntD 组件对接：建立一套受控组件适配层（逐步）

---

## ADR-010 Mock：MSW

- **决策**：开发与测试使用 MSW
- **理由**：
  - 拦截网络层，最贴近真实请求
  - 让前端在后端不可用时仍可推进
- **替代方案**：
  - 本地写死假数据：不可持续
- **风险与缓解**：
  - mock 与真实接口偏离：用 OpenAPI 生成类型/契约校验

---

## ADR-011 测试：Vitest + React Testing Library + Playwright

- **决策**：
  - 单测/组件测：Vitest + RTL
  - E2E：Playwright
- **理由**：
  - 工具现代、速度快
  - RTL 更贴近用户行为
  - Playwright 稳定，适合关键路径覆盖
- **替代方案**：
  - Jest：成熟但速度慢
  - Cypress：也可
- **风险与缓解**：
  - 测试脆弱：只测关键路径与稳定模块，不追求覆盖率虚高

---

## ADR-012 微前端：qiankun（按业务域拆分）

- **决策**：微前端使用 qiankun
- **理由**：
  - 治理能力强（加载、隔离、生命周期）
  - 落地案例多，适合 ToB 多团队
- **替代方案**：
  - Module Federation：更轻，但治理要自己补
  - iframe：隔离强但体验与通信差
- **风险与缓解**：
  - 复杂度上升：只有在域边界清晰、确实需要独立发布时再拆

---

## ADR-013 Next.js：辅线（帮助中心/文档站）

- **决策**：Next.js 仅用于辅助站点，不替代主线 SPA
- **理由**：
  - ToB 中后台大多不需要 SSR
  - Next 的收益集中在 SEO/静态内容/少量服务端能力
- **替代方案**：
  - 全站 Next：成本更高
- **风险与缓解**：
  - 维护两套体系：通过反向代理路由与共享鉴权口径降低心智负担
