# 00 起点评估与准备：后端 → 企业级前端的迁移地图

本章目标：让你用**后端工程师的思维**快速建立前端的“系统观”，并把环境、工具链、补课路径一次性配置好。

---

## 0.1 你需要建立的前端心智模型（对标后端）

| 后端概念              | 前端对标概念                               | 你要掌握到什么程度                          |
| --------------------- | ------------------------------------------ | ------------------------------------------- |
| Controller / API 网关 | BFF / API Client / 请求层封装              | 错误码分层、重试/取消、token 刷新、缓存策略 |
| DTO/VO/校验           | TS 类型 + Zod 校验 + 表单状态              | 类型建模与运行时校验一致，减少“前端口胡”    |
| RBAC/鉴权/审计        | 路由守卫/权限组件/按钮权限/埋点审计        | 做到：不可见/不可点/不可请求一致            |
| 缓存（Redis）         | 浏览器缓存 + Query Cache + SW/离线         | 缓存键、失效策略、并发一致性                |
| 线程/并发             | 事件循环、微任务/宏任务、并发渲染（React） | 不求论文级，但能定位常见卡顿/竞态           |
| 日志/链路追踪         | 前端日志、Sourcemap、错误监控、埋点        | 能闭环定位线上 JS 错误与性能退化            |
| 单元测试/集成测试     | 单测/组件测/E2E + Mock（MSW）              | 知道边界：哪些必须测，哪些不必测            |

## 0.2 必备工具链（企业主流）

### Node / 包管理

- Node：建议使用 **LTS 版本**（以企业常见为准，后续可用 nvm-windows 管理多版本）
- 包管理：**pnpm**（更快、更适合 monorepo）

### IDE 与调试

- JetBrains IDE（你已在用）：
  - 配置 TypeScript Language Service
  - 配置 ESLint/Prettier 自动修复
  - 熟悉 Chrome DevTools：Network / Performance / Memory / Coverage

### Git 与协作规范（从第一天开始）

- 分支：`main` + `feat/*` + `fix/*`
- 提交：Conventional Commits（例如 `feat: add login page`）
- PR：必须包含截图/录屏、测试点、影响面、回滚说明

## 0.3 前端必修基础的“最小集”（不要无边界发散）

> 你每周只有 10 小时，目标是“够用且能交付”。

### Web 运行时（够用即可）

- DOM / 事件模型（捕获/冒泡/委托）
- 事件循环：microtask/macrotask
- 浏览器渲染：reflow/paint/composite
- 网络：HTTP 缓存、CORS、Cookie/SameSite

### TypeScript（企业落地需要的能力）

- 基础：类型推断、联合/交叉、泛型、类型守卫
- 工程：`strict` 模式、`tsconfig` 常用项
- 建模：接口返回、分页、字典、权限矩阵、表单模型
- 与运行时校验一致：Zod（或同类）

### CSS（中后台常见问题优先）

- Flex/Grid
- 响应式与布局（中后台也会遇到）
- BFC/层叠上下文/定位
- 工程：CSS Modules / Less（AntD 常见）

## 0.4 你的“第一天”验收标准（环境是否可用）

1. 能创建并运行一个最小 Vite + React + TS 项目（后续我们会在第 2 月搭企业模板）
2. IDE 保存能自动格式化（Prettier）并提示 lint（ESLint）
3. Chrome DevTools 能定位：
   - 某个接口请求失败的原因（网络/跨域/鉴权/响应体）
   - 某个页面渲染慢的原因（长列表/重复渲染/布局抖动）

## 0.5 Java 后端协作预设（你现在就要带着这些口径学）

> 你的优势是后端背景：把接口契约、错误码、鉴权、审计这些从一开始就对齐。

建议你在后端（或 mock）里提前约定：

- **统一响应结构**（示例，仅供口径）：
  - `code`：业务码（非 200/500）
  - `message`：用户可读文案（或 key）
  - `data`：业务数据
  - `traceId`：链路/排查
- **分页/排序/过滤**：
  - `pageNo/pageSize` 或 `page/limit`
  - `sortBy/sortOrder`
  - 过滤字段明确为“白名单”
- **鉴权与刷新**：
  - Access Token + Refresh Token
  - 刷新并发策略（只允许一次刷新，其他请求等待）
- **权限数据模型**：
  - 菜单（route）
  - 操作（action/button）
  - 资源（resource/api）
  - 数据范围（dept/tenant/owner/field）

这些会在第 4 月的 RBAC 落地里变成可运行代码。

## 0.6 推荐你采用的学习方法（避免“看懂了但写不出”）

- 每个知识点必须对应一个“项目中的落点”（代码文件/模块/页面）
- 每周固定一次复盘：
  - 本周新增了哪些能力？
  - 哪些坑复现了？如何写成 checklist 防止再踩？
  - 哪些代码该重构？为什么没重构（时间/风险）？

---

## 0.7 进入主线前的自测题（你不需要全会，但要知道怎么查）

- 解释：为什么 React 列表渲染会卡？你会从哪几个角度定位？
- 解释：为什么同一个请求会被发两次？可能是 StrictMode？还是 effect 依赖？
- 实操：如何实现“token 过期自动刷新 + 并发请求只刷新一次”？
- 实操：如何实现“按钮权限/路由权限/数据权限”三者一致？
